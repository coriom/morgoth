# Experimental hierarchical browser planner

## Hypothesis and baseline

The operator-reported direct-action inventory trace was `CLICK C02` (new controls), `CLICK C02` (no visible change), `FILL C03` (change), `FILL C03` (no change), `CLICK C02` (no change); the controller stopped a loop with five actions and three no-change observations. The Llama 3 8B trial also failed the reviewed task after an irrelevant initial choice. These traces identify unproductive *decisions* on those trials, not hidden reasoning or a controller defect. The direct action source already receives the objective, trusted synthetic inputs, current bounded rendered observation, issued action choices, worker-confirmed history, ineffective-action suppression and remaining budget. It must infer a task-relevant intermediate outcome and choose an executable action in the same response.

The P1 hypothesis is that an explicit, bounded intended outcome may focus later choices. It costs at least one extra model call and can itself be wrong. No claim of improved real-model task completion follows from the implementation or scripted tests.

## Contracts and authority

`SubgoalProposal` is strict Pydantic data: `decision` (`pursue` or `abstain`), bounded `subgoal`, optional exact `visible_marker`, and bounded `uncertainty`. Native Ollama JSON Schema is supplied; tools and streaming are disabled. Duplicate JSON keys, extra fields, malformed output, URLs, control characters and incoherent abstention fail closed. The source sends only the objective, trusted target, bounded current UI observation and verified history. It receives no browser-worker handle, grants, filesystem tools or external destination authority.

The low-level selector is the existing `OllamaBrowserActionSource`. The subgoal is advisory context; the model still selects only a controller-issued action ID. The existing policy resolves that ID against the current observation and the worker rechecks the live DOM, element state, task-bound value and origin immediately before acting. Page content, subgoal text and a model claim of success never establish permission or mission completion. Independent rendered-state acceptance remains the only success test.

After a worker-acknowledged action, a deterministic advisory status marks a no-change subgoal for replanning, recognizes a literal visible marker as *visibly satisfied but unverified*, marks no available action as impossible, or leaves changed UI progress uncertain. A marker is model-proposed text, so its appearance does not prove semantic progress. Changed UI without a marker retains the current subgoal to conserve calls; a no-op requires a new one. This intentionally simple heuristic is a hypothesis to test, not a general semantic progress evaluator. The controller's existing repeated-action and cycle checks remain authoritative.

The six-call ceiling counts high- and low-level requests together. A fresh subgoal plus action requires two available calls; a retained subgoal requires one. Both layers use the same selected installed Ollama model, existing 60-second cold / 45-second loaded first-request and 35-second follow-up deadlines, with no retry or provider fallback. A two-request turn can take up to 95 seconds, so the worker input wait is 105 seconds; the parent interactive deadline remains 260 seconds with a five-second request margin. The maximum number of browser actions is therefore five after one high-level call, and fewer if replanning occurs. The first low-level request is not started if fewer than two calls remain for a new subgoal.

This adapter is opt-in and synthetic-only. It is not connected to autonomous START, research Brain, production permissions or persistent Project capability records. The operator experiment remains nonpersistent. Bubblewrap private networking and disposable Chromium profile remain; Chromium's internal sandbox is disabled inside Bubblewrap and no browser cgroup memory cap is proven. Real websites and accounts remain unsupported.
